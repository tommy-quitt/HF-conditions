# Deviations from SPEC.md

`SPEC.md` assumes a persistent server topology: a Next.js server, PostgreSQL, and a
long-running collector process holding open an MQTT connection (PSKReporter) and two
Telnet connections (RBN, DX Cluster) continuously (SPEC.md §7.2-7.4, §23, §33).

This project runs entirely on GitHub Pages (static hosting) + GitHub Actions (scheduled
jobs) — no dedicated server. GitHub Pages cannot run server code, and GitHub Actions
jobs are short-lived, so nothing can hold a persistent connection open. Per SPEC.md
§37 ("preserve the intended product behavior, isolate the discrepancy behind an
adapter, document the issue, implement the safest practical fallback"), each
persistent-connection requirement is adapted as follows. Everything else in SPEC.md
(scoring formulas, weights, confidence, no-LLM rule, region resolver interface, testing
requirements, UI principles) is implemented as written.

| Spec assumption | Adapted to | Why |
|---|---|---|
| Persistent MQTT feed (PSKReporter, §7.2) | Scheduled HTTP GET against PSKReporter's query/retrieval endpoint every ~10-15 min | No persistent connections are possible in a scheduled Actions job. A 10-15 min poll is not the "aggressive polling" the spec cautions against with that same endpoint. **Discovered from a real Actions run** (worked fine locally, not reproducible from a home network): the endpoint returned `403 Forbidden` from a GitHub Actions runner. PSKReporter's own developer docs ask automated clients to identify themselves via `appcontact` "so the operator can identify and contact you about problems" - the adapter wasn't sending that (it's only set when `HF_CONTACT_EMAIL` happens to be configured) or any `User-Agent` at all, which a WAF/bot-protection layer in front of a datacenter-IP request (GitHub Actions runners live in cloud ASNs) is more likely to block than an unidentified-but-residential-IP request. Fixed in `scripts/adapters/pskreporter.ts` by always sending a descriptive `User-Agent`. **Caveat, not yet confirmed**: if the block turns out to be purely ASN-based rather than header-based, this fix won't be enough - that would need a non-datacenter egress path (e.g. a self-hosted runner), which is a real architecture constraint to revisit if the next scheduled run still 403s. Setting the `HF_CONTACT_EMAIL` repo variable is also recommended per PSKReporter's own etiquette guidance, independent of whether it fixes this specific block. |
| Arbitrary per-viewer QTH for PSKReporter evidence (§3/§8) | Collector queries one fixed home grid (`KM72`, overridable via `HF_HOME_GRID`), not the viewer's actual QTH | Verified live: `retrieve.pskreporter.info/query` is scoped by `callsign`/`receiverCallsign`/`callsign+modify=grid` — there is no "give me everything, globally, for the last N minutes" query, unlike NOAA. A scheduled collector can't know an arbitrary future viewer's QTH in advance. Considered three options (fixed collector-side grid; live per-viewer client-side query via PSKReporter's documented `callback=` JSONP parameter, which works and sidesteps the missing CORS headers; a hybrid of the two) and the user chose the fixed grid for V1. Consequence: PSKReporter evidence in V1 is only meaningful for viewers near `KM72` — a viewer QTH far from it will see locality weights collapse toward 0 for this source (SPEC.md §8's own distance cutoff), not a bug, an accurate reflection of what was actually collected. **Generalized on the `experiment/client-side-pskreporter-query` branch** (not yet on `main`): the browser now also queries PSKReporter directly for the viewer's own grid via a real `<script>`-tag JSONP request (`apps/web/src/adapters/pskreporter-live.ts`) — `fetch()` can't be used here since the endpoint sends no CORS headers (still true from a real browser origin, not just assumed), but JSONP script-tag loads aren't subject to CORS. The pure query-building/response-parsing logic that both the Node collector adapter and this new browser client share now lives in `@hf-conditions/core`'s `external/pskreporter-format.ts` (still no network/fs access there, per AGENTS.md - only the transport differs per environment). **Verified live end-to-end** (real `vite preview` build, driven by a real Chromium browser via an ad hoc Playwright check, not retained as a dependency): the JSONP request against the real `retrieve.pskreporter.info` succeeds from an actual browser origin, ~1s round-trip, real reception reports returned and bucketed against the viewer's own QTH. On success this fully replaces the fixed-`KM72` buckets for that viewer; on failure (timeout, script load error, or an empty/malformed response) it falls back to the collector's fixed-grid snapshot rather than showing no PSKReporter evidence at all, and the UI reports which mode is active ("live for your QTH" vs. "showing collector snapshot"). **Open risk, not yet verified**: this was only checked from one real desktop-Chromium/home-network vantage point. Whether PSKReporter's endpoint behaves the same from every real visitor's browser/network (mobile carriers, corporate proxies, ad/tracker blockers that may target third-party `<script src>` tags, or the same kind of WAF/ASN-based blocking seen from GitHub Actions' datacenter IPs) is unconfirmed — the graceful fallback exists precisely because this can't be fully verified in advance for arbitrary real visitors. This also knowingly steps outside AGENTS.md's normal "external systems only via collector adapters" rule, deliberately and only for this one file, because per-viewer QTH access is the entire point of moving it client-side. |
| Persistent Telnet feed (RBN, §7.3) | Short (~60-90s, configurable via `HF_RBN_COLLECT_MS`) connect-collect-disconnect burst each scheduled run against `telnet.reversebeacon.net:7000` (the CW/RTTY skimmer feed) | RBN has no live HTTP alternative (only previous-day zip archives at reversebeacon.net/raw_data/). This samples the stream rather than continuously monitoring it — spots arriving between runs are lost. Verified live: the Telnet protocol itself is a simple "enter your call" prompt followed by a plain-text spot stream (`DX de <skimmer>: <freq kHz>  <spotted call>  <mode>  <SNR> dB  ... <HHMM>Z`), parsed and normalized in `scripts/adapters/rbn.ts`. RBN requires a real login callsign (there's no anonymous global query), configured via `HF_RBN_CALLSIGN` — collection is skipped (not attempted with a fabricated callsign) when it isn't set. **Resolved**: a real scheduled Actions run successfully connected, logged in, and collected 363 real spots — GitHub Actions' shared runner IPs are accepted by `telnet.reversebeacon.net`. (Had they been blocked, `collectSpotSource`'s existing per-source try/catch would have marked RBN degraded/disconnected and renormalized the remaining sources per §15/§19/§26 with no code change needed - every source is already isolated this way.) **FT8 feed** (SPEC.md §7.3: "where useful") runs on a separate RBN port and is deliberately not collected in V1 — CW/RTTY skimmer coverage alone is already independent evidence distinct from PSKReporter's (mostly FT8) reports; this is a documented gap, not a silent one. |
| Real per-callsign geolocation for RBN (§7.3: "Resolve station locations where possible") | A small hand-built table (`scripts/adapters/callsign-location.ts`) mapping ~100 internationally allocated callsign prefix blocks (ITU/IARU country allocations — factual, publicly documented assignments, not a licensed dataset) to one coarse representative coordinate per prefix, longest-prefix-match | RBN's Telnet feed gives only bare callsigns — no grid square (PSKReporter) or pre-resolved lat/lon (HolyCluster). The real per-station DXCC/CTY dataset is still the same deliberately-deferred piece from TASKS.md step 3 (`createDxccRegionResolver` takes an empty table in V1); building it out was pushed to "when a collector needs it," and RBN is the first source that actually does. This coarse table is consistent with `packages/core`'s own `REGION_REPRESENTATIVE_POINTS` (also a coarse per-region sanity check, not a precise model) but coarser again since it's per-prefix, not per-region — a Chinese callsign and a Mongolian one both resolve to Asia correctly, but two callsigns from different, far-apart parts of the same country resolve to the same point. Verified live end-to-end against the real feed (`HF_RBN_CALLSIGN=N0CALL npm run collect`): 34 real RBN spots collected and normalized in a 20s test burst; 0 of them bucketed for the KM72 (Israel) fixed QTH in that particular sample, since with country-centroid-level precision only spots involving an actual `4X`/`4Z` station (or, more generally, one within `LOCALITY_MAX_KM` of Israel) can register as "local" — not a bug, an honest consequence of both the fixed-QTH simplification above and this coarse geocoding. |
| Persistent Telnet connection to a DX Cluster node (§7.4) | Scheduled HTTPS GET against `holycluster.iarc.org/history?start_time=&end_time=` (UNIX seconds - an ISO timestamp 422s) | Verified live: an unauthenticated public JSON endpoint that already aggregates several standard DX-Spider/AR-Cluster/CC-Cluster nodes (see its own `telnet_servers.csv`) and returns pre-resolved `[lon, lat]` coordinates and numeric DXCC codes per spot - no locator parsing needed. Caveat: third-party, undocumented, unlicensed, no stated SLA. A raw multi-node Telnet-burst adapter (same pattern as RBN) is the documented fallback if this service becomes unavailable. Its feed also blends in POTA/WWFF/SOTA activator spots alongside classic manual DX-cluster spots (visible via a `type` field) - V1 treats all of it as one `dxCluster` evidence source, since it's all human-initiated activity reporting, per SPEC.md §7.4's characterization. Unlike PSKReporter, this endpoint is a genuine global firehose for the requested time window, not scoped to a callsign/grid - so it doesn't carry the fixed-QTH limitation described below. **Observed from a real run**: 385 real spots collected in one 15-minute window, 0 bucketed for a KM72 (Israel) QTH - checked live, this was genuine (the closest spot was 1,299 km away, just outside `LOCALITY_MAX_KM`'s cutoff, which was 1,200km at the time - see the row below for why it's since been raised), not a bug. Being a global firehose doesn't guarantee *local* evidence every run - unlike PSKReporter (which, being queried specifically for the fixed home grid, is structurally the more reliable per-location source when it's working). RBN's coarse callsign-prefix geocoding (see below) has the same "0 buckets despite real spots" failure mode, for a related but distinct reason. |
| `LOCALITY_MAX_KM` = 1200km (§8's own suggested value) | Tried 4000km, then reverted back to 1200km (`packages/core/src/weighting.ts`) | SPEC.md §8 explicitly frames this as a tunable constant, not a scientific fixed value ("make both 600 and 1200 configuration constants"). Raised to 4000km based on a real DX Cluster observation (see the row above): 1,200km was cutting off a genuinely-relevant 1,299km-away spot, and 4000km did produce real DX Cluster evidence on the next run (27 buckets vs. 0). That change also surfaced a discussed-but-unresolved side effect: `LOCALITY_SIGMA_KM` (decay rate) was left at 600km, so a distant (e.g. 3,500km) spot passed the wider cutoff and counted fully toward diversity (`uniqueStationCount`, an unweighted `Set.add`) despite an activity weight (`weightedSpotCount`) of essentially 0 - not a bug, just an asymmetry between the two halves of the evidence formula worth being aware of if it's revisited. **Reverted to 1200km** at the user's request after a subsequent run still showed no PSKReporter evidence (a separate, still-open problem - PSKReporter is grid-scoped to `HF_HOME_GRID` so its evidence should be local by construction regardless of this cutoff; the widened radius wasn't the fix for that). If DX Cluster/RBN evidence for the fixed QTH goes back to being sparse/zero often, that's this revert, not a new bug. |
| `condition_snapshots` table for trend history (§21, §24) | Browser `localStorage`, scoped per QTH (`apps/web/src/score-history.ts`) | Trend compares the current score with the score 15 minutes ago, but scores are computed client-side per viewer QTH (see the `GET /api/conditions` row below) - there's no server-side table to keep that history in. Each refresh (every 5 min, SPEC.md §25) records that viewer's own scores locally and looks up the entry closest to 15 minutes ago (within a 3-minute tolerance) the next time. Consistent with SPEC.md §21's "never fabricate a trend": with no qualifying local entry yet (e.g. first load, or `localStorage` unavailable/cleared), `trend` stays `null` exactly as `packages/core`'s `trend()` already models it - it does not silently start over at "stable". |
| PostgreSQL (§23, §24) | Committed JSON files in a dedicated `data` branch, pruned each run | Matches V1's own modest retention needs (~60-120 min raw, small aggregates); avoids running a database with nothing to host it on. |
| Next.js server + `GET /api/conditions` (§22, §23) | Static JSON evidence feed + the same `packages/core` scoring engine run client-side in the browser | Per-viewer QTH determines locality/direction weighting, so the final matrix can't be precomputed once for every grid square. Shipping the evidence and running the (already pure, deterministic, network-free) scoring engine in the browser reproduces the same typed contract without a live server. |
| Live `GET /api/health` (§31) | Static `health.json` written each collection run | Reports "as of the last scheduled run" rather than an instantaneous socket status — call this out in the UI copy rather than implying a live probe. |
| Continuous `apps/collector` daemon (§23, §33) | `scripts/collect.ts`, invoked by a GitHub Actions scheduled workflow | Same normalization/aggregation responsibilities, just re-triggered per run instead of running forever. |
